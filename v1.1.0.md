# Vibrance MusicLib 1.1.0: plan

Status: **planned, not started.** This is the owner's to-do list for the next minor release. Each item says why it is wanted, what was decided, what to do and when it is done. Items are ticked as they land; the file is removed, or reduced to a pointer to [CHANGELOG.md](CHANGELOG.md), once 1.1.0 is released.

The project rules in [AGENTS.md](AGENTS.md) still apply to every item: keep it simple, no new moving part without a reason, tests only where data safety or an API contract is at stake, and the UI budget of 90 KB of CSS plus JavaScript (uncompressed, fonts excluded). **The budget is tight:** `web/*.css` and `web/*.js` weigh 79,209 bytes today, so the whole release has about 10 KB to spend. Measure with `wc -c web/*.css web/*.js` after every UI item.

Suggested order: the password login first (it is the only breaking change and the docs depend on it), then the theme switch and the gradients, then the reverse proxy and library checks, and the documentation rewrite last, when the behavior it describes is final.

## 1. Password login

**Why.** MusicLib has no authentication: it relies on the loopback binding. Someone who sets `MUSICLIB_BIND=0.0.0.0` to use it from another device, or who publishes it through a proxy without authentication, leaves the whole library editable by anyone on the network. A single password, configured in `.env` like the one of Pi-hole, closes that mistake without adding users.

**Decisions.**

- **One password, no user name.** There is one user; a user name adds no security. The login form has only a password field.
- The password comes from `MUSICLIB_PASSWORD` in `.env`, passed to the app by `compose.yaml`.
- **Mandatory, also when upgrading from 1.0.0.** The server refuses to start without it, or with fewer than 12 characters, with a clear log line saying what to set and where. This is a breaking change and the CHANGELOG says so at the top of the 1.1.0 section.
- Only the server needs it: the offline commands (`doctor`, `rebuild`, `backup`, `restore`, `version`, `healthcheck`) keep working without it.
- Sessions live **in memory**: a restart signs the user out. No table, no migration, no signing key to store.

**To do.**

- [ ] Read `MUSICLIB_PASSWORD` at boot of the server subcommand; refuse a missing, empty or shorter than 12 characters value with a stable error code. Never log the value.
- [ ] Login page (`GET /login`) in the existing layout style, with a password field that password managers recognize (`autocomplete="current-password"`), and a sign-out button in the sidebar.
- [ ] `POST /login` compares the password in constant time. A failed attempt waits about one second before answering, and attempts are handled one at a time, so guessing is slow without per-IP bookkeeping.
- [ ] On success, a random session id (32 bytes from `crypto/rand`) in a cookie: `HttpOnly`, `SameSite=Strict`, `Path=/`, `Secure` when `PUBLIC_ORIGIN` is `https`. A fixed maximum age (for example 30 days); sign-out removes the session.
- [ ] Every page and API route requires a session, except `/login`, `/static/*` needed by the login page, `/health/live` and `/health/ready` (the Compose healthcheck uses them). Pages redirect to `/login`; the API answers `401` with the usual `{code, message, details}` body.
- [ ] The Host and Origin checks stay in front of everything, `/login` included. The login form cannot send `X-Musiclib-Request: 1` as a plain HTML form: either submit it with `fetch` like the rest of the UI, or exempt `/login` from that header only, keeping the `Origin` check. Choose the simpler one and write down why.
- [ ] `compose.yaml`: pass `MUSICLIB_PASSWORD` to the app. `.env.example`: add it, empty, with a comment. The install block of the README and of `docs/operations.md`: generate one (`openssl rand -base64 24`) the same way it already generates `POSTGRES_PASSWORD`, and tell the user how to read it (`grep MUSICLIB_PASSWORD .env`).
- [ ] Tests (this is an API contract): no session means `401`/redirect on every protected route; health endpoints stay open; a wrong password is refused; the cookie flags follow `PUBLIC_ORIGIN`; the boot refuses a missing or short password; sign-out invalidates the session.
- [ ] Update the rules in **both** `AGENTS.md` and `CLAUDE.md`: the API boundary section ("no authentication") becomes "one password from `MUSICLIB_PASSWORD`, sessions in memory"; the configuration list gains `MUSICLIB_PASSWORD`; "users and roles" stays out of scope.
- [ ] Docs: how to set and change the password (edit `.env`, then `docker compose up -d --wait`), and why HTTPS matters: over plain HTTP on a LAN the password travels in clear, so remote or shared-network use goes through the reverse proxy of item 4.

**Done when** a fresh install and an upgrade from 1.0.0 both lead to a working login, and the gate passes.

## 2. Theme switch: light, dark, system

**Why.** Today the theme follows only the operating system (`prefers-color-scheme`). The user wants to choose it from the interface.

**Decisions.**

- **Three states:** light (sun), dark (moon) and system (the default). One button in the sidebar cycles through them; its icon and accessible label show the current state. With the sidebar collapsed it shows the icon only, like the other entries.
- The choice is remembered **per browser in `localStorage`**, the same mechanism `web/sidebar.js` already uses for the collapsed sidebar. That script runs in `<head>` before the first paint, so setting `data-theme` on `<html>` there avoids a flash of the wrong theme and needs no server change and no inline script (the CSP forbids it).

**To do.**

- [ ] `web/sidebar.js`: read `musiclib.theme` (`light`, `dark`, or absent for system), set `data-theme` on `<html>` before the body is parsed, handle the button click, and keep working when storage is unavailable (then the theme follows the system).
- [ ] `web/app.css`: apply the dark tokens when `[data-theme="dark"]`, or when no theme is chosen and the system is dark (`@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) { … } }`). Consider writing each token once with `light-dark()` and switching `color-scheme` instead of duplicating the dark block; keep whichever is smaller and clearer.
- [ ] Keep `<meta name="color-scheme">` coherent with the choice, so form controls and scrollbars follow it.
- [ ] Three small icons (sun, moon, half-filled circle or screen for system) as `<symbol>`s in `web/layout.html`, drawn like the existing ones.
- [ ] Check both themes on every page (Library, Album, Import, Activity, login). No new tests (UI look).

## 3. Gradients: violet grain in the sidebar, cover colors on the album page

**Why.** The interface is clean but anonymous. A violet, grainy sidebar gives the app its own identity, and an album page tinted with the colors of its cover makes each album feel like itself.

**Decisions.**

- **Static gradients, no animation**, to keep the page light.
- **The cover colors are extracted in the browser**, from the cover image already on the page, with a `<canvas>`. The image has the same origin, so the canvas is readable. No database column, no migration, no server work, nothing to backfill for existing albums.
- The gradient is **background only**: it is mixed with the page color, cards and text keep solid surfaces, and every text keeps at least WCAG AA contrast in both themes.

**To do: sidebar.**

- [ ] A gradient toward violet, derived from the brand accent (`--accent`, hue about 288 in OKLCH), with a light and a dark variant.
- [ ] Grain: the CSP (`default-src 'self'`) blocks `data:` images, so the texture is a small file served with the other static assets (an SVG tile with `feTurbulence`, or a pre-rendered PNG tile of a few KB), repeated, at low opacity. Measure the rendering cost; prefer the PNG tile if the SVG filter is slow on large screens.
- [ ] Check the contrast of the navigation labels, the active entry and the focus ring on top of it.

**To do: album page.**

- [ ] When the cover has loaded, draw it scaled down (for example 32 × 32) on a canvas, group the pixels into coarse color buckets, and pick two or three frequent, reasonably saturated and distinct colors, skipping near-white and near-black.
- [ ] Set them as CSS custom properties on the album page (for example `--album-1`, `--album-2`, `--album-3`); the CSS builds the gradient with `color-mix()` toward `--paper`, so it adapts to light and dark.
- [ ] Fade the gradient in (`--slow`) once the colors are known, so nothing jumps.
- [ ] Fallbacks: no cover, a cover that fails to load or decode, or no JavaScript: a gradient from the brand violet.
- [ ] Update the colors after a cover change without reloading the page.
- [ ] Budget: the whole item should stay within about 3–4 KB of CSS and JavaScript. No new tests (UI look).

## 4. Reverse proxy and a domain name

**Why.** To reach MusicLib as `https://music.example.com` from other devices, with HTTPS, the documented path must be short and copyable. The design already fits: with Caddy, `PUBLIC_ORIGIN=https://music.example.com` is enough, because Caddy forwards the original `Host` and sets no upload size limit.

**Decisions.** No new service in `compose.yaml`: the proxy stays optional and lives in the documentation as ready-to-copy examples.

**To do.**

- [ ] Verify end to end with Caddy: pages, login cookie with `Secure`, imports, cover and attachment uploads of the maximum size, downloads. If everything works, no code change is needed; if something fails, fix it and add a test for the API contract involved.
- [ ] Document **Caddy on the same host**: a two-line `Caddyfile` (`music.example.com { reverse_proxy 127.0.0.1:8080 }`), `PUBLIC_ORIGIN` in `.env`, and `MUSICLIB_BIND` left at `127.0.0.1` so only Caddy reaches the app.
- [ ] Document **Caddy in Docker** next to MusicLib: a `compose.override.yaml` snippet (which Compose merges automatically) with the Caddy service on the same network, `reverse_proxy app:8080`, and no published app port.
- [ ] Document a **LAN-only name** (for example `music.home.arpa`) with `tls internal`, and what trusting Caddy's local certificate authority means on each device.
- [ ] A short note for other proxies: they must pass the original `Host`, must not rewrite `Origin`, and must allow large request bodies (nginx defaults to 1 MB: set `client_max_body_size`).
- [ ] Replace "put an authenticated reverse proxy in front (outside this application's scope)" in the README and the docs with the new model: the password of item 1 protects the app, the proxy adds a name and HTTPS.

## 5. Reading the library from a host folder

**Why.** The generated `library/` should be easy to reach from the host, so other applications can read it, without digging into Docker's storage.

**What already exists.** `MUSICLIB_DATA=/srv/musiclib/data` in `.env` keeps all of `/data` in a host folder, and the library is then `/srv/musiclib/data/library`, readable by every user (the app writes with umask 022).

**Decision: only `MUSICLIB_DATA`, no separate library path.** `/data` must be one filesystem without nested mounts, because publication relies on atomic `renameat2` within it; mounting `library/` alone somewhere else would break that guarantee. The one manual step, `chown` of the new folder to uid 1000, stays: doing it automatically would need root in the container, which the rules forbid. The docs give the exact command to copy.

**To do.**

- [ ] Document, with a complete example, choosing a host folder **before the first start**: create it on ext4, `chown`, set `MUSICLIB_DATA`, start, and find the library at `<folder>/library`.
- [ ] Document **moving an existing installation** from the named volume to a host folder. Two candidates: a backup restored into a new empty folder and a new database (already supported, see "Restoring next to an existing installation" in `docs/operations.md`), or a stopped-app copy of the volume with ownership preserved (`cp -a`) followed by `doctor`. Test both on a throwaway installation, and document only the one that is verified and simpler.
- [ ] State clearly that other programs may **read** `library/` but must never write into it (tags, covers, index or thumbnail files): the next render replaces it. Check what happens at the next publication when a foreign file appears inside an album folder or an artist folder, and document the outcome.
- [ ] Check that the boot error for a folder with the wrong owner names the expected uid and the command to fix it; improve the message if it does not.

## 6. Documentation rewrite: one linear guide

**Why.** `docs/docker.md` (871 lines) mixes installation, tests, pins, release procedure, API examples and leftovers of the development rounds (a heading still says "round 16"); `docs/operations.md` is dense and hard to follow in order. A longer guide that reads from top to bottom, with examples, is better than two short, tangled ones.

**Decisions.**

- **`docs/operations.md` becomes the single guide for whoever runs MusicLib**, in the order a user needs it.
- **`docs/docker.md` becomes the guide for developers only**: build, test gate, test storage, services and profiles, pins, releasing.
- The README stays a short introduction with the install block and links into the guide. No new documentation files.

**To do.**

- [ ] Rewrite `docs/operations.md` in this order, with a concrete example for each step:
  1. What you need (Linux, ext4, Docker Engine with Compose).
  2. Install: the one-block install, what it creates, how to open the app and sign in.
  3. Configuration: every `.env` variable in one table with its default and an example (`POSTGRES_PASSWORD`, `MUSICLIB_PASSWORD`, `PUBLIC_ORIGIN`, `MUSICLIB_BIND`, `MUSICLIB_PORT`, `MUSICLIB_DATA`, `MUSICLIB_BACKUP`, `MUSICLIB_IMPORT`, `MUSICLIB_UID`/`MUSICLIB_GID`, `WORKERS`).
  4. Where your files are, and reading the library from a host folder (item 5).
  5. The password (item 1).
  6. Access from other devices: LAN, and a domain with HTTPS through Caddy (item 4).
  7. Importing and the Activity page.
  8. Backups, restore, and moving to another folder or machine.
  9. Upgrading, including the 1.0.0 → 1.1.0 step (set `MUSICLIB_PASSWORD`).
  10. Maintenance: `doctor` and `rebuild`, when and how.
  11. Troubleshooting: each refusal at boot or error code a user can meet, what it means and what to do.
  12. The API, with `curl` examples (moved here from `docs/docker.md`).
- [ ] Strip `docs/docker.md` of user material, remove the round leftovers, and point to `docs/operations.md` for running the app.
