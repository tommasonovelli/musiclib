# Vibrance MusicLib: rules for contributors and agents

These are the rules and principles for anyone who changes this repository, human or AI agent. `AGENTS.md` and `CLAUDE.md` have identical content: change both together. User-facing documentation is in [README.md](README.md) and [docs/operations.md](docs/operations.md); the developer guide is [docs/docker.md](docs/docker.md).

## What MusicLib is

A personal, single-user music library manager. It imports album folders from a read-only `/import` mount, keeps every imported file as an immutable, content-addressed original, lets the user correct artists, albums, tracks, covers, attachments and lyrics in a browser, and generates `library/`: ordinary folders and tagged FLAC, MP3 and M4A (AAC/ALAC) files for any player to read. It is one Go server (`musiclibd`) with embedded HTML/CSS/JS, PostgreSQL 17, a small C++ TagLib helper and pinned FFmpeg, shipped as a Docker image and run with Docker Compose. **Few features, done well**: simplicity is a permanent requirement, not a phase.

## Build, test, run: Docker only

- The host needs only Docker with the Compose v2 plugin. Never install Go, gcc, CMake, TagLib, FFmpeg or PostgreSQL on the host. On Windows, run the scripts from Git Bash and keep LF line endings.
- `scripts/check.sh [packages]` is the gate: `sqlc diff`, `go build`, `go vet`, `gofmt`, `go test -race` against a real PostgreSQL 17 (`postgres-test`) with `TMPDIR` on a real ext4 volume, no network. It tests a snapshot of the tree taken at build time. A host `go test` that skips database tests proves nothing.
- `scripts/dev.sh [cmd]` runs a shell or one command in the toolchain container on the live sources (e.g. `scripts/dev.sh go test -race -count=20 -run TestX ./internal/publish`).
- `scripts/sqlc.sh` regenerates `internal/store` after any change in `sql/` or `migrations/`; the generated code is committed. `scripts/lint-shell.sh` after changing shell scripts; `scripts/fuzz.sh Target duration [pkg]` for fuzz targets.
- `check.sh`, `dev.sh` and `fuzz.sh` always use `compose.dev.yaml` and need no `.env`; the maintenance wrappers (`doctor.sh`, `rebuild.sh`, `backup.sh`, `restore.sh`) act on the installation's Compose file. To run the app from source: `docker compose -f compose.dev.yaml up -d --build --wait`, then open `http://127.0.0.1:8080/`.
- Details, pins and the release procedure: [docs/docker.md](docs/docker.md).

## Owner's working rules

- **Keep it simple.** Prefer the least complex option that works, even when a more automatic one is nicer. Every new moving part (service, file, setting, mechanism) must be justified, and flagged explicitly when proposed.
- **MusicLib is autonomous.** It must work perfectly on its own. No awareness of, reference to, or design choice driven by any music player or future integration, in code, docs, comments or commits. "Vibrance" appears only as part of the product name "Vibrance MusicLib".
- **Tests only where data safety is at stake**: storage, import, render/publish, recovery, maintenance and API contracts. No new tests for UI look, branding, copy or docs; minimal edits to existing tests that assert changed text are fine.
- **No temporary data-migration code in the repository.** One-off fixes of existing data are run by hand, outside the repository. Permanent rules belong in the code (e.g. a render that fills a missing value is a permanent rule, not a migration script).
- **Migrations are forward-only.** Never edit or remove a migration that has been released or applied anywhere; add a new one. No down migrations; an older binary refuses a newer schema (`store_schema_too_new`), and a downgrade is a restore of an older backup.
- **English only** for code, identifiers, comments, logs, errors, tests, docs, commit messages and the UI. Some legacy code comments quote the original Italian specification; they are translated only when that code is changed for another reason (see the end of this file).
- **UI budget:** CSS plus JavaScript under 100 KB, uncompressed, fonts excluded. No frontend build, Node, CDN, SPA framework, WebSocket or SSE.
- **The sun logo is outside the MIT License** (all rights reserved, see [LOGO.md](LOGO.md)); everything else original is MIT. Third-party material keeps its own license and notices.
- **Decisions are recorded in commit messages and `CHANGELOG.md`**, not in separate decision logs.

## Invariants (non-negotiable)

### Where the truth lives

- PostgreSQL holds the desired catalog (names, relations, managed tags, cover choice, attachments), the job queue and the publication journal.
- `/data/originals/` holds the immutable bytes of every imported or uploaded file, named by SHA-256.
- `/data/library/` is output only: never read back as a source, never imported, fully replaced by a render. Manual edits there are lost.
- `/data/work/` holds temporary builds, blob temporaries and retired directories.

### Storage and volume

- Linux and local ext4 are requirements; all of `/data` is one filesystem with no nested mounts, and the boot verifies it (same device, a real `renameat2(RENAME_EXCHANGE)`). No fallback with weaker guarantees for NFS, NTFS or other filesystems.
- One application instance per database and data volume. An exclusive `flock` on `/data/.lock` is held by the server and by every offline command; `/data/.lock` is never deleted.
- `/data/.musiclib-store` and `settings.store_id` pair the volume with its database; a mismatch is refused and a marker is never rewritten automatically.
- `/data/.maintenance` (rebuild/restore in progress) blocks the boot until the same operation completes; it is never removed by hand.
- `/import` is a separate read-only mount outside `/data`; `/backup` is outside `/data` too.
- Free space: every import, build and upload reserves its conservative size estimate in one process-wide budget (`internal/jobs`), and starts only if the free space of `/data`, minus a 1 GiB safety margin and every other reservation, covers it; otherwise it fails with `insufficient_space` (`507` for an upload). The budget is not a guarantee: every write still handles `ENOSPC`, a disk that fills up during a build leaves the published album and the originals intact, and nothing published or original is ever removed to make room.

### Originals and blobs

- One put primitive (`internal/blobstore`): temp file in `work/blobs`, hash while copying, `fsync`, checked `close`, re-read and verify, `renameat2(RENAME_NOREPLACE)` into the shard, fsync of the directories.
- An existing blob is verified before being trusted; a mismatch is `corrupt_blob`, never an overwrite. A fixed blob is never modified or deleted by the application; there is no garbage collector, and unreferenced blobs are information, not errors.
- Blobs become durable before any transaction references them.

### Import

- The import source is never modified, moved or deleted. Only directories under `/import` are accepted, as relative paths; the API accepts no host path.
- Symlinks and special files are never followed. A source that changes during an import makes the import fail.
- Import is atomic per album: every track is fully decoded and verified before the commit; album, tracks, attachments, reservations, the render job and the job's outcome are written in one transaction.
- A fingerprint of the candidate's files detects repeated imports (`skipped`), never merged. Artists are never merged implicitly.
- Tracks can also be uploaded into an existing album, one file at a time, verified by the same code as an import (`importer.ReadTrack`) outside any transaction, then appended in one change of the album. A byte-identical file already in the album is refused (`track_exists`), never merged implicitly.

### Catalog and concurrency

- Every change that alters an album's output increments its revision and enqueues its render in the same transaction; a no-op save changes nothing.
- All catalog mutations take the same transaction-scoped PostgreSQL advisory lock (the catalog lock). It serializes short SQL decisions only: no media or tool I/O inside a catalog transaction.
- A path belongs to one album only: `path_claims` reserves the desired, published and in-flight paths before commit. Conflicts are explicit errors (`409`), never resolved by random suffixes, adoption or deletion of foreign directories.
- One render job row per album; workers claim with `FOR UPDATE SKIP LOCKED`; completion is conditional on the claimed ticket, so a stale result never completes a newer request.
- An artist left without any album (trashed albums count) is deleted in the transaction that moves its last album away, or that empties the trash of its last album.
- A move of tracks changes both albums in one transaction under the catalog lock: both revisions bumped, both renders enqueued. An album left without tracks goes to the trash in that transaction; only a trashed album may have no tracks, and it cannot be restored then.
- Emptying the trash (`POST /api/trash/empty`, one catalog transaction) deletes the catalog rows of the trashed albums whose removal from `library/` is complete (no published path, no render job, no journal), never an original or a blob row. An album whose removal is still pending, running or failed waits; nothing deletes trashed albums automatically.
- Serialization failures and deadlocks retry the short transaction (at most three times, with jitter). A lost database connection or an uncertain commit is never retried blindly: the process stops workers and mutations, exits, and recovers on restart.

### Render and publication

- A render builds the **complete** album in `work/render/<build_id>` from the catalog snapshot and the originals; the plan is a pure function of the snapshot and `render_version` (no I/O).
- Every copy is verified against its blob hash. For each track: decoded-PCM digest before tagging, tag write, re-read of managed and unmanaged tags, digest after; any difference fails the render. Tags are written only on staging copies.
- Managed tags are rewritten completely (absent value = removed); unmanaged tags are preserved, and a field the helper cannot preserve fails the render instead of being lost.
- `.musiclib.json` is a derived receipt (ids, revision, `render_version`, file hashes), never a source of catalog data.
- One publication at a time under `publishMu`, lock order `publishMu` then catalog lock: PREPARE (journal row committed) -> INSTALL (`RENAME_NOREPLACE` / `RENAME_EXCHANGE`, retire the old directory to `work/retired`) -> FINALIZE (published state from the journal's values). A path shows the complete old or the complete new album, never a partial one.
- Recovery at boot runs before any worker and completes forward using the receipt to recognize an installed build; it never repeats an exchange. A disk state that matches no legal step suspends publishing (`publish_illegal_state`, readiness 503): nothing is guessed or deleted. Offline `rebuild` is the universal recovery of derived output.
- The published revision is always the revision that was built, never "the current one".

### Names

- `internal/names` normalization (NFC, sanitization, 180-byte components with hash suffix, casefold keys) is frozen. Changing it needs a key migration and a conflict check, not only a new `render_version`.
- Fixed layout: `<artist>/<album>/[Disc N/]NN - <title>.<ext>`, `cover.jpg|png` at the album root, every attachment under `Extras/`. Collisions after normalization are explicit errors naming both sides; no file is dropped or renamed silently.

### Filesystem access

- All filesystem access goes through `internal/fsops`: directory descriptors and `openat2` with `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS`. Never `filepath.Join(root, input)` followed by trusting path operations; name sanitization is not confinement.
- Never ignore an error from `close`, `fsync`, `rename` or `commit`. Durability steps are fsyncs of files and of their directories.

### Pins and `render_version`

- Every image, tool and module the repository uses is pinned by exact version (images also by digest, source tarballs by sha256); never `latest` or a floating tag. The published app image in `compose.yaml` is the one exception, pinned by its release version without a digest.
- Stay on Go 1.25.x and `golang.org/x/text` v0.41.0: x/text's Unicode tables feed the frozen name keys.
- `render_version` is derived from the renderer revision, the names algorithm, the Go toolchain, FFmpeg, the helper and TagLib versions. Any change that can alter a byte of the output bumps the matching input (`internal/render/version.go`); tests pin them, and the boot refuses tools at other versions.

### API and browser boundary

- `PUBLIC_ORIGIN` is mandatory: `Host` must match it (`421`), `Origin` if present must equal it (`403`); every non-GET/HEAD request needs `X-Musiclib-Request: 1`, except the two plain HTML forms `POST /login` and `POST /logout`, which keep the Host and Origin checks. No CORS, `nosniff` everywhere, CSP `default-src 'self'`.
- Artist and album resources carry strong ETags (`"album:<id>:<revision>"`); every change of an existing artist or album (covers, attachments, tracks and manual renders included) needs `If-Match` (`428` without, `412` if stale), checked in the transaction of the change. No last-write-wins. The rule covers changes of existing artists and albums only: creating an artist or an import, `POST /api/render-all` (it changes no revision), `POST /api/trash/empty` (it deletes only albums whose removal is complete) and the job actions (retry, retry of all failed jobs, dismiss) take no `If-Match`. A move of tracks needs the `If-Match` of the source album only: the destination is only appended to and its revision bumped, so its open editor gets `412` on its next save.
- Errors are `{code, message, details}` with stable codes; no absolute paths, SQL or full stderr in responses. JSON bodies reject unknown and duplicate keys.
- Downloads go by entity id, never by a client-supplied path; arbitrary files are served as attachments.
- One user, one password: `MUSICLIB_PASSWORD` (at least 12 characters, no user name), read by the server only; the offline commands, `version` and `healthcheck` run without it, and the server refuses to start without it (`password_invalid`). Sessions live in memory (a restart signs out): a random 32-byte id in the cookie `musiclib_session` (`HttpOnly`, `SameSite=Strict`, `Secure` with an https `PUBLIC_ORIGIN`), 30 days from the sign-in. The password is compared in constant time, one attempt at a time, and a refused attempt holds the turn for one second. Every route needs a session except `/login`, `/logout`, `/static/*` and the health endpoints: pages redirect to `/login`, the API answers `401 login_required`. The password, the cookie and session ids are never logged. Loopback binding by default; over plain HTTP the password crosses the network in clear, so remote or shared-network access goes through an HTTPS reverse proxy.

### Container and operations

- Configuration comes only from the environment: `DATABASE_URL`, `PUBLIC_ORIGIN`, `HTTP_ADDR`, `WORKERS`, and `MUSICLIB_PASSWORD` for the server. Container paths are fixed (`/data`, `/import`, `/backup`).
- The database password is defined once per Compose file (`x-db-password`): `POSTGRES_PASSWORD` from `.env`, else the default `musiclib`, which the docs tell users to change before the first start. The app receives it as `PGPASSWORD` (read by pgx) and `DATABASE_URL` carries none.
- Never root: `musiclibd` refuses uid 0 and sets umask 022; the app container runs without capabilities, with a read-only root filesystem. PostgreSQL keeps `fsync`, `full_page_writes` and `synchronous_commit` on and publishes no port.
- `doctor`, `rebuild`, `backup` and `restore` run offline (app stopped, PostgreSQL up) and take the volume lock. Doctor never repairs; restore only into a new empty database and volume, never over an installation; backups are never overwritten.

## Code style

- Small functions with explicit inputs and outputs; concrete types; interfaces only at boundaries useful for tests. Dependencies are passed in constructors.
- One implementation each of normalization, blob put, enqueue and publication.
- The planner does no I/O, the store knows no absolute paths, the tag helper knows no domain.
- Typed errors with stable codes and context. `context.Context` in the signature of every long operation.
- All SQL lives in `sql/*.sql` through sqlc; catalog writes go through the transactional services, never ad-hoc SQL in handlers or workers.
- No ORM, DI container, event bus, CQRS, job framework, microservice, external queue, cache or speculative configuration. Optimizations must keep the protocol and come from measurements.
- Tests use the real thing where it matters: real PostgreSQL, real ext4, the real kernel and the pinned tools; failpoints and real process kills for the crash matrix. Mutation-check important invariants (break the code, watch a test fail). Fixtures must be redistributable.

## Out of scope

Playback, streaming, transcoding of published files, online lookup or music recognition, two-way sync, filesystem watchers, users and roles, plugins, general history or undo, automatic merges, editing arbitrary tags, `move` imports, whole-library uploads from the browser, artist images, deletion of originals or a blob garbage collector, heuristic `feat.` parsing, replicas or multiple instances.

## How to work

- Read the code you change and the relevant guide in `docs/`. Keep changes focused; update documentation together with any change of behavior or guarantees.
- Verify with `scripts/check.sh` (whole module for code changes) and repeat new or touched concurrency tests with `scripts/dev.sh go test -race -count=N`. Documentation-only changes need no gate: check links, commands and `git diff --check`.
- Never touch a running installation: its `musiclib_db`, `musiclib_data` and `musiclib_backup` volumes hold real data. Use `stop`, never `docker compose down -v`; tests use `postgres-test` and the `testdata` volume only.
- Never commit `.env`, credentials, personal music, catalog dumps or screenshots of private data.
- No player references, no speculative features, no scope creep: when unsure, choose the simpler and more conservative option and say so in the commit message or report.
